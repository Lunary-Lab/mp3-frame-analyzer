# Tests, fuzzing, and performance

## Test pyramid

1. **Unit**: table-based validation of bitrate, rate, padding, CRC bit, invalid indices, reserved flags and synchsafe ID3 lengths.
2. **Property-based**: fast-check generates valid VBR sequences, random payloads, and arbitrary chunk boundaries. The invariant is that every generated frame is counted exactly once regardless of chunk partitioning. Reproducible seeds and minimized counterexamples come from fast-check.
3. **Integration**: Fastify `inject()` exercises multipart parsing, content type, limits, validation, JSON response and status codes.
4. **Real HTTP**: a listening server receives multipart `FormData` via Node's native `fetch`.
5. **Regression**: three real FFmpeg/libmp3lame fixtures: CBR and VBR with Xing/Info metadata (33 physical frames each), plus CBR without Xing metadata (51 physical frames).
6. **Security**: oversized upload, malformed multipart, forged filename, invalid frame/header and metadata corruption.

## Mutation smoke versus coverage-guided fuzzing

`scripts/fuzz-parser.mjs` deterministically mutates a real VBR fixture and creates arbitrary junk data, checking for unexpected exceptions, invalid success counts, and reproducibility. It accepts only typed `Mp3ParseError` as a legitimate rejection. A valid count is not asserted for arbitrary malformed input because the generated bytes have no independent truth oracle.

It is a bounded **mutation smoke test**, not coverage-guided fuzzing. The separate Jazzer.js 4 targets provide coverage feedback; `fast-check` and the structured Jazzer target additionally check known-correct frame counts.

To reproduce a failing mutation input use `FUZZ_CASES` with the deterministic PRNG and failing index/seed recorded in the output.

## Performance measurements

- `npm run bench` reports Vitest CBR/VBR microbenchmarks; speed is informational.
- `npm run test:memory` runs independent processes at approximately **8, 32, and 128 MiB**. The source produces distinct owned 64 KiB chunks of a real MP3 fixture. No file-sized source buffer or aliased repeated chunk can hide retaining the entire input. Each run reports exact frame count, RSS/OS high-water mark, heap, external memory, array buffers, throughput, and delay of a pending event-loop callback.
- The memory gate checks both absolute peak growth and additional growth between the smallest and largest inputs. Limits allow normal GC/JIT and runner variation while making retained 128 MiB inputs exceed the bounds. This measures input-size scaling at a fixed upstream chunk size; it does not establish a universal process-memory ceiling.
- `npm run test:performance` owns a local server in a separate process, sends two concurrent valid uploads of approximately 32 MiB, and issues small valid uploads while they run. Correct counts, JSON content type, completion, and clean server exit are required. Upload/probe latencies and server event-loop delays are reported without a timing pass/fail threshold.
- `k6 run bench/upload.k6.js` is optional for longer local experiments. It requires zero incorrect/failed responses. Use the default loopback address or an environment you explicitly operate.

The parser-memory source has no artificial scheduling sleeps: an immediately ready source can defer other callbacks until parsing completes. The HTTP experiment measures actual socket/backpressure behavior separately. Neither result justifies calling performance optimal or treating a few requests as a statistical capacity estimate. Associate results with Node version, hardware, runtime load, input size, and chunk size. The parser's linear traversal and bounded buffering remain appropriate for this task.

CI saves JSON performance measurements as workflow artifacts. Investigate a sustained regression on a controlled runner before introducing a latency SLA or a microbenchmark speed gate.

## Manual tool cross-check

FFprobe's `nb_read_frames` counts frames that its decoder-facing demuxer accepts as audio. Xing/Info metadata-bearing MPEG frames can be omitted from this count. For our two audio fixtures it reports 32 audio frames versus 33 structurally present MPEG frames. The difference is intentional and should be explained rather than dismissed as incorrect parsing.

Generate a new fixture independently:

```bash
ffmpeg -f lavfi -i 'sine=frequency=440:sample_rate=44100:duration=0.8' \
  -ac 1 -c:a libmp3lame -b:a 128k -id3v2_version 4 new-fixture.mp3
```

The actual assessment sample has been independently checked. It is not redistributed because it contains third-party music; use `ASSESSMENT_SAMPLE_PATH` for the optional identity-and-count test described below.

## Independent format cross-check (2026-10-24)

The core TypeScript parser was compiled independently and checked against nine
FFmpeg/libmp3lame files at 32 kHz, 44.1 kHz, and 48 kHz. At each rate we
compared CBR, VBR and a CBR encoding with `-write_xing 0`. FFprobe decoded
38, 51 and 56 audio frames respectively. Files with Xing/Info each contained
one additional physical MPEG frame; files without Xing matched the decoder
count. Every structural count matched, including across 127-byte chunks.

These generated fixtures complement the actual assessment MP3. The supplied sample was subsequently verified as described below.

## Native coverage-guided fuzzing (Jazzer.js 4)

The original 2,000-case mutation smoke is still useful but does not use
coverage feedback. The added Jazzer.js `raw` and `structured` fuzz targets do.
The raw target checks chunk-partition invariance and treats typed domain errors
as valid rejections. The structured target generates valid frames independently
and asserts an exact count, including metadata and CRC/padding variants.

Use `npm run fuzz:regression` for deterministic corpus replay, `npm run
fuzz:coverage` for bounded PR fuzzing, and `npm run fuzz:extended` for the
longer on-demand campaign. The timeouts and crash-reduction workflow are
documented in [`fuzz/README.md`](../fuzz/README.md). A failure from libFuzzer
or the process watchdog is never marked successful. Curated byte-level
regressions in `fuzz/regressions/raw` are replayed by Vitest and have
explicit expected errors; `.fuzz-corpus` and minimized crashes remain outside
Git until reviewed. The fast-check properties include metadata boundaries,
truncation, bit-field invalidity, concatenation, and arbitrary byte partition
invariance. Use `PROPERTY_SEED` and `PROPERTY_PATH` to replay shrunk cases.

## Coverage and mutation baseline before release hardening (October 24, 2026)

With additional boundary tests, **the four core parser modules have 100%
statement/branch/function/line coverage**; total `src/mp3/**` + `src/app.ts`
coverage is 97.07% branches and 98.13% statements. No branches were ignored
to achieve this result. The remaining HTTP branches are defensive and are not
deleted merely for a score.

Mutation testing uses [Stryker](https://stryker-mutator.io/) with the **command
runner** (not its Vitest 5 runner, which has a documented test-name-filtering
regression: https://github.com/stryker-mutator/stryker-js/issues/6210).
Run `npm run mutation`. It deliberately targets the MPEG header and ID3
decoder, where a changed bit, size or error code is meaningful. Do not equate
100% coverage with 100% mutation score; inspect surviving non-equivalent
mutants and add focused tests, without excluding difficult cases to inflate
the score.

The measured Stryker score rose from **76.92% to 97.90%**, after tests for
invalid MPEG sync patterns, ID3 signature and revision handling, and reserved
flag boundaries. That baseline run killed 138 mutants, timed out on 2, and left
3 provably equivalent survivors in ID3 validation. CI now enforces a 95%
minimum for the deliberately limited two-decoder mutation scope. See
[the mutation audit](mutation-review.md) and [the passing GitHub run](https://github.com/Lunary-Lab/mp3-frame-analyzer/actions/runs/40102747242).

The assessment's actual MP3 is checked optionally when
`ASSESSMENT_SAMPLE_PATH` is set. It is not checked into Git because it
contains third-party music. SHA-256
`97707a18a58ba75122b1668f5ed738f090121343432d9172a6409ddfa4fc5ab3`
identifies the specific 1,458,172-byte file. Structural frame count: **6090**;
FFprobe decoded-frame count and MediaInfo `FrameCount`: **6089** (the first
frame carries the Xing header, whose declared count is 6089). See

## Upload lifecycle and release verification

HTTP tests cover the accepted MIME types, malformed multipart classification, rejected text/additional file parts, exact file-limit boundaries, sanitized application failures, cancellation, continued service after rejection, and demonstrated keep-alive connection reuse, including pipelined requests behind a large upload that the parser rejected early. Shutdown tests exercise successful close hooks, rejected hooks, the drain deadline, invalid startup configuration, and a real child process receiving SIGTERM on POSIX. A transport abort is not asserted to produce an application JSON response.

`npm run check` includes helper-tool tests and builds the application. `npm run package:release` packages that existing build, verifies version agreement, and generates checksums and a production CycloneDX SBOM. `npm run test:artifact` verifies the digests, installs production dependencies in a temporary unpacked directory, starts `dist/server.js`, checks a real HTTP upload, and observes graceful shutdown. This guards against source-only npm tarballs that omit `dist/`. The GitHub Release workflow reuses the complete CI gates for the exact tagged commit and uploads the same tested artifact bytes.

## Free-format, raw upload and metadata-header policy

The same `POST /file-upload` endpoint accepts raw `audio/mpeg` (also `audio/mp3` and `application/octet-stream`) or single-file multipart bodies. HTTP tests cover both modes, default/optional counting, 413 errors for known-length and chunked streams, and invalid query values. Independent frame constructors exercise free-format MPEG-1 Layer III across supported sample rates and padding variations, including constant spans without padding (48 kHz and 32 kHz at round bitrates), malformed alignment, decoy sync bytes and truncation. When `lame` is installed, real encoder output is also checked at 400 kbps, 320 kbps, 192 kbps and 128 kbps across all three sample rates. The count option `includeVbrHeaderFrame=false` excludes only a structurally verified initial Xing/Info/LAME or VBRI encoder header, never an arbitrary payload match or a declared VBR count. The supplied sample oracle remains 6090 by default and 6089 with exclusion. Truly short free-format streams without enough header evidence fail closed rather than guessing. Real free-format LAME fixtures may be reproduced with `lame --freeformat -b 400 input.wav output.mp3` and decoded with `lame --decode` for independent confirmation; FFprobe may not recognize above-table free-format bitrates.
