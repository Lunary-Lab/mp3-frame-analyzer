# Tests, fuzzing, and performance

Maintained runtime and tooling code also follow the enforced
[complexity and size limits](code-quality.md). Boundary tests verify that the
production gates fail at 11 complexity, 301 file lines, 61 function lines, and
121 characters, while retaining the documented test and literal exceptions.

## Test pyramid

1. **Unit**: table-based validation of bitrate, rate, padding, CRC bit, invalid indices, reserved flags and synchsafe ID3 lengths. A table drives `errorResponseFor` through every failure mechanism, and stub consumers drive the upload module's guarantees.
2. **Property-based**: fast-check generates valid VBR sequences, random payloads, and arbitrary chunk boundaries. The invariant is that every generated frame is counted exactly once regardless of chunk partitioning. Reproducible seeds and minimized counterexamples come from fast-check.
3. **Integration**: Fastify `inject()` exercises multipart parsing, content type, limits, validation, JSON response and status codes.
4. **Real HTTP**: a listening server receives multipart `FormData` via Node's native `fetch`.
5. **Regression**: three real FFmpeg/libmp3lame fixtures: CBR and VBR with Xing/Info metadata (33 physical frames each), plus CBR without Xing metadata (51 physical frames).
6. **Security**: oversized upload, malformed multipart, forged filename, invalid frame/header and metadata corruption.

## Mutation smoke versus coverage-guided fuzzing

`scripts/fuzz-parser.mjs` deterministically mutates a real VBR fixture and creates arbitrary junk data, checking for unexpected exceptions, invalid success counts, and reproducibility. It accepts only typed `Mp3ParseError` as a legitimate rejection. A valid count is not asserted for arbitrary malformed input because the generated bytes have no independent truth oracle.

It is a bounded **mutation smoke test**, not coverage-guided fuzzing. The separate Jazzer.js 4 targets provide coverage feedback; `fast-check` and the structured Jazzer target additionally check known-correct frame counts.

To reproduce a failing mutation input use `FUZZ_CASES` with the deterministic PRNG and failing index/seed recorded in the output.

## Performance measurements

- `npm run bench` reports Vitest CBR/VBR microbenchmarks; speed is informational.
- `npm run test:memory` runs independent processes at approximately **8, 32, and 128 MiB**. The source produces distinct owned 64 KiB chunks of a real MP3 fixture. No file-sized source buffer or aliased repeated chunk can hide retaining the entire input. Each run reports exact frame count, RSS/OS high-water mark, heap, external memory, array buffers, throughput, and delay of a pending event-loop callback.
- The memory gate checks both absolute peak growth and additional growth between the smallest and largest inputs. Limits allow normal GC/JIT and runner variation while making retained 128 MiB inputs exceed the bounds. This measures input-size scaling at a fixed upstream chunk size; it does not establish a universal process-memory ceiling.
- `npm run test:performance` owns a local server in a separate process, sends two concurrent valid uploads of approximately 32 MiB, and issues small valid uploads while they run. Correct counts, JSON content type, completion, and clean server exit are required. Upload/probe latencies and server event-loop delays are reported without a timing pass/fail threshold.
- `k6 run bench/upload.k6.js` is optional for longer local experiments. It requires zero incorrect/failed responses. Use the default loopback address or an environment you explicitly operate.

The parser-memory source has no artificial scheduling sleeps: an immediately ready source can defer other callbacks until parsing completes. The HTTP experiment measures actual socket/backpressure behavior separately. Neither result justifies calling performance optimal or treating a few requests as a statistical capacity estimate. Associate results with Node version, hardware, runtime load, input size, and chunk size. The parser's linear traversal and bounded buffering remain appropriate for this task.

CI saves JSON performance measurements as workflow artifacts. Investigate a sustained regression on a controlled runner before introducing a latency SLA or a microbenchmark speed gate.

## Manual tool cross-check

FFprobe's `nb_read_frames` counts frames that its decoder-facing demuxer accepts as audio. Xing/Info metadata-bearing MPEG frames can be omitted from this count. For the CBR and VBR fixtures it reports 32 audio frames versus 33 structurally present MPEG frames. The HTTP default and explicit `includeVbrHeaderFrame=false` return 32 for these fixtures; `true` returns 33. The no-Xing fixture returns 51 under all three HTTP options. Direct parser calls retain their physical-frame default. These policies are tested separately rather than assuming every tool counts the same thing.

Generate a new fixture independently:

```bash
ffmpeg -f lavfi -i 'sine=frequency=440:sample_rate=44100:duration=0.8' \
  -ac 1 -c:a libmp3lame -b:a 128k -id3v2_version 4 new-fixture.mp3
```

The actual assessment sample has been independently checked. It is not redistributed because it contains third-party music; use `ASSESSMENT_SAMPLE_PATH` for the optional identity-and-count test described below.

## Native coverage-guided fuzzing (Jazzer.js 4)

The original 2,000-case mutation smoke is still useful but does not use
coverage feedback. The added Jazzer.js `raw` and `structured` fuzz targets do.
The raw target checks chunk-partition invariance and treats typed domain errors
as valid rejections. The structured target independently constructs frames with
known boundaries and asserts exact physical and metadata-excluded counts,
including free-format, metadata, CRC and padding variants. These are structural
fixtures; their payloads are not asserted to be decodable audio.

Use `npm run fuzz:regression` for deterministic corpus replay, `npm run
fuzz:coverage` for bounded PR fuzzing, and `npm run fuzz:extended` for the
longer on-demand campaign. The timeouts and crash-reduction workflow are
documented in [`fuzz/README.md`](../fuzz/README.md). A failure from libFuzzer
or the process watchdog is never marked successful. Curated byte-level
regressions in `fuzz/regressions/raw` are replayed by Vitest and have
explicit expected counts or errors; `.fuzz-corpus` and minimized crashes remain outside
Git until reviewed. The fast-check properties include metadata boundaries,
truncation, bit-field invalidity, concatenation, and arbitrary byte partition
invariance. Use `PROPERTY_SEED` and `PROPERTY_PATH` to replay shrunk cases.

## Upload lifecycle and release verification

HTTP tests cover the accepted MIME types, malformed multipart classification, rejected text/additional file parts, exact file-limit boundaries, sanitized application failures, cancellation, continued service after rejection, and demonstrated keep-alive connection reuse, including pipelined requests behind a large upload that the parser rejected early. Shutdown tests exercise successful close hooks, rejected hooks, the drain deadline, invalid startup configuration, and a real child process receiving SIGTERM on POSIX. A transport abort is not asserted to produce an application JSON response.

Deployment configuration tests cover the absent 50 MiB default, decimal syntax,
positive/safe-integer boundaries, and rejected empty, malformed, signed,
fractional, unsafe and unlimited values. Real `src/server.ts` child-process tests
verify invalid configuration exits before listening and a configured limit accepts
one byte below and exactly at the boundary, then rejects one byte above, for
known-length raw, chunked raw and multipart file bytes. An unfinished declared
oversize raw request is rejected immediately, and the server still accepts the
next valid upload.

`npm run check` includes helper-tool tests and builds the application. The build removes generated `dist/` first, so renamed or deleted source modules cannot linger in the runtime archive; a tooling regression renames a source module between two builds and verifies the obsolete output is gone. `npm run package:release` packages that existing build, verifies version agreement, and generates checksums and a production CycloneDX SBOM. `npm run test:artifact` verifies the digests, installs production dependencies in a temporary unpacked directory, starts `dist/server.js`, checks 76 real HTTP scenarios, verifies liveness after rejected uploads and keep-alive recovery, and observes graceful shutdown without leaked children. This guards against source-only npm tarballs that omit `dist/`. The GitHub Release workflow reuses the complete CI gates for the exact tagged commit and uploads the same tested artifact bytes.

## Free-format, raw upload and metadata-header policy

The same `POST /file-upload` endpoint accepts raw `audio/mpeg` (also `audio/mp3` and `application/octet-stream`) or single-file multipart bodies. HTTP tests cover both modes, default/optional counting, 413 errors for known-length and chunked streams, and invalid query values. The owner-selected HTTP default and explicit `includeVbrHeaderFrame=false` exclude only a structurally recognized initial Xing/Info or VBRI encoder header; `true` requests physical counting. No arbitrary payload match or declared VBR count changes the answer. The supplied sample's HTTP expectations are 6089 for omitted/`false` and 6090 for `true`; the low-level parser's default remains 6090.

Independent frame constructors exercise free-format MPEG-1 Layer III across supported sample rates and padding variations, including constant spans without padding (48 kHz and 32 kHz at round bitrates), malformed alignment, decoy sync bytes and truncation. Five fixed genuine LAME encodings are always checked at 400 kbps, 320 kbps, 192 kbps and 128 kbps across all three sample rates, including parser mutation. The required Node 24 validation step regenerates and decodes those exact fixtures with `node scripts/encoder-fixtures.mjs`; a missing or different encoder fails rather than skipping coverage. Short free-format streams without enough header evidence are rejected. The bounded acquisition rule selects a unique greatest header-match score; it does not establish that no other plausible header-only partition exists. Real free-format LAME fixtures may be reproduced with `lame --freeformat -b 400 input.wav output.mp3` and decoded with `lame --decode` for independent confirmation; FFprobe may not recognize above-table free-format bitrates.

## HTTP error taxonomy and adversarial framing

The taxonomy itself is unit-tested in `tests/error-response.test.ts`; the HTTP tests below prove the framework really raises those failures, including multipart forms cut off inside or after the upload bytes. Real socket and Fastify-injection tests verify that Fastify-generated unsupported media types are classified as 415, empty raw/multipart bodies are classified as 400, multipart file/field/part limits are distinguished from file byte limits, and unknown methods return 405 with `Allow: POST` while unknown paths stay 404. Raw early-error responses close their connection instead of draining an unbounded body; multipart rejections continue to exercise pipelined keep-alive. The tests also distinguish a transport-level cancellation or mismatched advertised HTTP length (which might not produce any JSON response) from an application-level malformed MP3 response, and they verify that the server remains operational after the client disconnects. Expected error precedence follows the first observed error for streaming content.
