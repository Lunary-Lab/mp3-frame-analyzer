# Tests, fuzzing, and performance

## Test pyramid

1. **Unit**: table-based validation of bitrate, rate, padding, CRC bit, invalid indices, reserved flags and synchsafe ID3 lengths.
2. **Property-based**: fast-check generates valid VBR sequences, random payloads, and arbitrary chunk boundaries. The invariant is that every generated frame is counted exactly once regardless of chunk partitioning. Reproducible seeds and minimized counterexamples come from fast-check.
3. **Integration**: Fastify `inject()` exercises multipart parsing, content type, limits, validation, JSON response and status codes.
4. **Real HTTP**: a listening server receives multipart `FormData` via Node's native `fetch`.
5. **Regression**: two real FFmpeg/libmp3lame fixtures (CBR and VBR) with an explicit structural count of 33 frames each.
6. **Security**: oversized upload, malformed multipart, forged filename, invalid frame/header and metadata corruption.

## Mutation smoke versus coverage-guided fuzzing

`scripts/fuzz-parser.mjs` deterministically mutates a real VBR fixture and creates arbitrary junk data, checking for unexpected exceptions, invalid success counts, and reproducibility. It accepts only typed `Mp3ParseError` as a legitimate rejection. A valid count is not asserted for arbitrary malformed input because the generated bytes have no independent truth oracle.

It is a bounded **mutation smoke test**, not a coverage-guided Jazzer.js campaign. The stronger structural oracle is the `fast-check` property suite in CI. A full coverage-guided fuzz campaign could be added for prolonged security hardening but is not necessary to run or assess the solution.

To reproduce a failing mutation input use `FUZZ_CASES` with the deterministic PRNG and failing index/seed recorded in the output.

## Performance measurements

- `npm run bench`: Vitest Bench compares CBR and VBR parsing for inputs of ~2 MiB.
- `npm run test:memory`: streams exactly 100,000 synthetic frames (41,700,000 bytes), reporting elapsed seconds, MiB/s, peak RSS growth, and Node version. The source reuses a constant-size frame rather than creating a file-sized Buffer.
- `k6 run bench/upload.k6.js`: optional HTTP benchmark with five concurrent clients uploading a bundled fixture. Reports request latency percentiles and response correctness. Run against a **local** server, not public services.

CI validates a *generous* upper RSS growth bound (64 MiB) for deterministic stream processing. Raw speed is informational, not a gating assertion on shared virtualized runners. Benchmark results should always be associated with Node version, CPU/machine, and environment.

## Manual tool cross-check

FFprobe's `nb_read_frames` counts frames that its decoder-facing demuxer accepts as audio. Xing/Info metadata-bearing MPEG frames can be omitted from this count. For our two audio fixtures it reports 32 audio frames versus 33 structurally present MPEG frames. The difference is intentional and should be explained rather than dismissed as incorrect parsing.

Generate a new fixture independently:

```bash
ffmpeg -f lavfi -i 'sine=frequency=440:sample_rate=44100:duration=0.8' \
  -ac 1 -c:a libmp3lame -b:a 128k -id3v2_version 4 new-fixture.mp3
```
