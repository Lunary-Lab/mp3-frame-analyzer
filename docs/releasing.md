# Versioning and releases

Releases distribute a versioned runtime archive through GitHub Releases. The npm package remains `private: true`; this workflow never publishes to the npm registry.

## Version authority

[Release Please Action v5](https://github.com/googleapis/release-please-action/blob/v5.0.0/README.md) maintains the release PR, changelog, package version, lockfile version, and `.release-please-manifest.json`. The manifest was initialized at **1.0.0**, with bootstrap commit `fa85190d2f4ad31453c32e90cff0b76ae432526a`. That was a version baseline, not a published 1.0.0 artifact; the first nonbreaking `feat` release advanced it to **1.1.0**. For the current source version, consult the package and release manifest rather than this historical initialization record. `last-release-sha` is an explicit commit-walk stop, not a permanent promise about future release boundaries. The pinned Release Please implementation stops at that SHA if it encounters it before the expected release commit. Keep the existing bootstrap and last-release anchors unchanged until the expected tag, manifest version, and ancestry have been verified; do not substitute an anchor for a release tag in generated comparisons.

Use Conventional Commit PR titles and **squash merge with the PR title as the commit title**. Release Please reads the resulting commits on `main`; PR labels do not provide a second versioning authority. The squash commit body defaults to **blank** because Release Please also parses commit bodies: a `BREAKING CHANGE:` note or a paragraph starting `fix:` copied from branch commits or a PR description would otherwise add releases the title did not declare. Mark breaking changes with `!` in the PR title; a deliberate `BREAKING CHANGE:` footer can still be typed into the merge dialog. Optional scopes describe the changed area without changing the bump. Dependabot uses `fix(deps):` for production dependency updates, `build(deps-dev):` for development-only updates, and `ci(deps):` for Actions updates.

| Squashed PR title                                                     | Effect                   |
| --------------------------------------------------------------------- | ------------------------ |
| `fix(api): correct multipart error classification`                    | Patch                    |
| `perf(parser): reduce header copying`                                 | Patch                    |
| `feat(parser): support appended metadata`                             | Minor                    |
| `feat(api)!: change the frame-counting contract`                      | Major                    |
| `docs: clarify setup`, `ci: update checks`, `chore: maintain tooling` | No release by themselves |

An intentional incompatible change to the JSON shape, documented status semantics, or accepted API contract requires a breaking-change marker. The owner-approved change from a physical-frame HTTP default to excluding one recognized initial Xing/Info/VBRI metadata frame changes that contract and requires a major release. It is structural exclusion, not audio decoding. Use a breaking PR title such as `feat(api)!: exclude initial encoder metadata by default`; let Release Please update the version, changelog, lockfile and release manifest. Correcting an implementation to its documented contract remains a fix.

## Two generated release-history views

One merged PR/commit history feeds two audiences; there is no second manually
maintained “internal changelog.”

- **[Changelog](../CHANGELOG.md):** Release Please owns the concise, user-facing
  history and version. `feat`, `fix`, `perf`, and `revert` entries describe behavior,
  fixes, compatibility, configuration, security, and migrations. Use ordinary
  `docs`, `test`, `refactor`, `build`, `ci`, or `chore` titles for internal-only
  work rather than disguising it as a user fix. Scopes alone do not filter entries.
  A user-visible security fix can be `fix(security): …`; incompatible configuration
  or runtime changes need `!` and actionable migration guidance. Breaking notes
  survive even when their commit type is normally hidden.
- **Engineering changes:** a collapsed section in the prepared GitHub release
  body, generated by GitHub's native release-notes API using
  [`.github/release.yml`](../.github/release.yml). It includes all merged PRs in the
  verified range, including refactoring, tests, CI, docs, dependencies, unlabeled
  changes, and release-preparation PRs. Labels organize this view; they do not
  determine the version. Nothing is excluded by author or label. Unlabeled PRs
  fall into **Other changes**, and release PRs have their own category rather
  than disappearing from the audit. PR entries gain merge-commit links;
  additional commits without a merged PR are listed separately. Both tag and
  immutable-SHA comparisons are included.

The source is the tagged `CHANGELOG.md` entry, not an editable draft release body.
Normally its comparison supplies the previous tag; both tags resolve to checked
full SHAs. A first successor release with no previous tag instead requires the
explicitly reviewed [initialization boundary](release-notes-initialization.md).
The previous SHA is exclusive and the current SHA inclusive. No date windows,
“latest release” guesses, automatic fallback tags, or new tags are used. A
missing uninitialized boundary, divergent history, a truncating Release Please anchor,
incomplete pagination, a missing or duplicate PR, or a changed tag stops
preparation. The complete compare-commit list, per-commit PR associations, and
independent closed-PR inventory are paginated and cross-checked before comparing
them with native notes. This is an audit of GitHub's recorded PR associations,
not an inference from `#123` text in commit messages.

Generation copies the user-facing entry without rewriting its breaking or
migration text and rebuilds the engineering section from scratch. It never
appends to a previously composed body or writes `CHANGELOG.md`. Repeating the
same inputs gives identical content; changed PR metadata produces new reviewable
bytes and therefore requires a new approval. API failures and oversized results
fail closed, rather than publishing a partial list.
For a standalone notes preview, rerun **all jobs** after a failure so every
input and output belongs to one attempt. For publication, start a **new dispatch**
instead: publication rejects every attempt after the first. Previously generated
artifacts or environment decisions are never reused to authorize a later attempt.

### Preparation and publication integration

[`release-notes.yml`](../.github/workflows/release-notes.yml) is a reusable,
non-publishing preparation workflow with `tag` and `sha` string inputs. Invoke it
from exact-tag validation with the same source SHA and require its successful
completion. The caller's permission ceiling must permit `contents: write`,
`pull-requests: read`, and `actions: read`; only the fixed native API job gets the write token, because
GitHub requires it for `POST /releases/generate-notes` even though that endpoint
saves nothing. That job has no checkout and runs no project code. Planning,
coverage checks, and composition execute with read-only permissions. Composition
uses `actions: read` to authenticate immutable artifact metadata before download.

[`publish-release.yml`](../.github/workflows/publish-release.yml) invokes preparation
and full runtime verification together, then seals their exact successful outputs
into one immutable `release-bundle-<tag>-1` artifact. The runtime interface returns
`release_artifact_id`, `release_artifact_digest`, and `release_run_attempt`;
notes return `artifact_id`, `artifact_digest`, and `body_sha256`. These interfaces
and their caller must change atomically. No consumer discovers an artifact by
name: metadata authenticates its immutable ID, digest, repository ID, producer
run/attempt and source before download, and the pinned downloader fails on digest
mismatch. The source manifest and all checksums are independently verified.

The notes producer artifact contains exactly `body.md` and `manifest.json`. Its
manifest records both boundary SHAs/tags, PR and direct-commit identities,
input/body hashes, and producer run, attempt and workflow SHA. The sealed bundle
preserves those bytes and the runtime's existing four files, adding
`release-identity.json` (both producer artifact IDs/digests, repository ID,
source/tag and run/attempt) and `BUNDLE-SHA256SUMS`. The latter describes the
structured Actions bundle, with `release/` and `notes/` paths; the original
`SHA256SUMS` remains the runtime-only, flat-download checksum list.

Provenance attests **all** sealed files: runtime archive, SBOM, both checksum
lists, runtime metadata, both notes views and their manifest, and identity ledger.
Only after successful validation, composition, sealing and attestation does the
single `release` environment job request one owner decision. The summary exposes
the exact source, run/attempt, input artifact IDs/digests, sealed bundle ID/digest,
and complete proposed body before that decision. The final job checks that the
configured reviewer and actual native approval are the explicitly reviewed owner
`choskeli` (ID `98036866`), not merely an arbitrary configured reviewer. There is
no administrator bypass and only `v*` tags may deploy.

After approval, that job downloads the **same sealed bundle** by authenticated
ID, rechecks all bytes and identities, then rechecks owner/environment decision,
tag and draft immediately before the single publication transition. It rejects
edited draft text, unexpected assets, missing/duplicate/wrong approvals, stale
source/run/attempt/repository/artifacts, and failed or skipped provenance.
Published asset digests and body are read back. It never executes project code,
rebuilds the runtime, retags, deletes releases or edits an existing published
release. A fresh dispatch always requires a fresh genuine owner approval; agents
must never approve it. Existing immutable v2.1.1 remains unchanged and does not
retroactively acquire this workflow or a new engineering view.

### Nonpublishing hosted prerequisite check

[`release-prerequisites.yml`](../.github/workflows/release-prerequisites.yml) runs
on relevant same-repository PRs, or explicit dispatch. It checks live environment,
artifact, digest and approval-history response shapes, exercises native generation
against an exact bounded commit range, verifies complete native PR coverage, and
tests ID-based artifact transport. Its native job has no checkout or artifact
download; the only POST is `releases/generate-notes`, which saves nothing. Its
preview label is never created as a Git tag. No job uses the release environment
or creates, edits, publishes or deletes a release. Fork PRs skip this write-token
prerequisite; normal read-only tests still run.

This checks real hosted API behavior, **not** a successful future publication or
owner approval. Offline execution tests use fake `gh` responses and cover negative
cases independently; they are not live validation. The prerequisite cannot prove
that a future tag's content/approval is correct. A real publication still needs
all exact-tag gates and the owner's single decision.

For a notes-only preview of a future tag already containing these workflows,
dispatch `release-notes.yml` at that exact tag with matching `tag` and `sha`.
Focused tests run with `node --test scripts/release-notes*.test.mjs scripts/release-publish.test.mjs`
and are included in `npm run test:tooling`.

The behavior above was checked against
[Release Please 17.6.0's commit boundaries](https://github.com/googleapis/release-please/blob/v17.6.0/src/manifest.ts),
[its default changelog generator](https://github.com/googleapis/release-please/blob/v17.6.0/src/changelog-notes/default.ts),
the pinned preset's
[breaking-note handling](https://github.com/conventional-changelog/conventional-changelog/blob/conventional-changelog-conventionalcommits-v6.1.0/packages/conventional-changelog-conventionalcommits/writer-opts.js),
and GitHub's
[native categorization](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)
and [generate-notes API](https://docs.github.com/en/rest/releases/releases#generate-release-notes-content-for-a-release).
The pinned action bundles Release Please 17.6.0; changing that pin requires
rechecking boundary and composition behavior, not assuming it is unchanged.

## Automated path

1. A merge to `main` runs `release-please.yml`. Its metadata-only job creates or updates the release PR; it does not check out project code.
2. The workflow explicitly dispatches **CI and Conventional Commit PR title validation at the release PR head** using `GITHUB_TOKEN`. This avoids relying on token-generated PR events or their approval-dependent runs. GitHub documents `workflow_dispatch` as an allowed trigger for this token in [Triggering a workflow](https://docs.github.com/actions/using-workflows/triggering-a-workflow). The dispatched check runs attach to the release PR's head commit, but GitHub does not list `workflow_dispatch` runs in the PR's checks tab. Review them from the `check-release-pr` job log, which prints both run URLs, or with `gh api repos/Lunary-Lab/mp3-frame-analyzer/commits/<head-sha>/check-runs`. GitHub also queues the token-created PR's ordinary `pull_request` CI as **awaiting approval**. Approving it (Actions → the run → _Approve and run_) adds a second, PR-visible validation of the merge ref; CI is read-only, so approval grants no write access.
3. Review and squash merge the release PR. Release Please creates a **draft release** and, with `force-tag-creation`, creates its `vX.Y.Z` tag while it is still a draft.
4. The workflow dispatches `publish-release.yml` **at that exact tag**, passing its full commit SHA. Preflight requires a matching draft, a matching tag commit already reachable from `main`, and `GITHUB_SHA` equal to the declared source commit. Dispatching from `main` is rejected.
5. The reusable, read-only CI validates that commit. It checks Node 24 and 26, npm compatibility, formatting, lint, both TypeScript compilers, coverage, tooling, mutation testing, fuzzing, dependency audits, static analysis, secrets, and measured memory/HTTP behavior. The Node 24 release lane packages the existing compiled output and tests the unpacked artifact; the publisher never rebuilds it.
6. Native notes preparation independently verifies the same release range. The candidate job seals the tested runtime and both notes views, with immutable input identities and checksums, into one artifact. Build provenance attests every sealed file.
7. The `publish` job waits in the `release` environment for one approval from the release approver ([Release approval](governance.md#release-approval)). After approval it authenticates and downloads the same sealed artifact, verifies its complete checksum/identity ledger, rechecks the owner decision, draft and tag, attaches the files and combined notes, and only then publishes the draft. A validation, attestation or approval that does not succeed leaves it unpublished.

The version verifier requires agreement between `package.json`, both lockfile root versions, the release manifest, and the supplied release tag. In CI, the recorded source commit must equal the checked-out Git HEAD. Tag-based invocation also keeps the standard attestation's workflow commit aligned with the actual build source.

## Published files

| File                                     | Contents                                                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `mp3-frame-analyzer-X.Y.Z.tar.gz`        | Compiled JavaScript, package metadata, lockfile, README, runtime instructions, and embedded release metadata |
| `mp3-frame-analyzer-X.Y.Z.cdx.json`      | CycloneDX application SBOM generated by `npm sbom --omit=dev --package-lock-only`                            |
| `mp3-frame-analyzer-X.Y.Z.manifest.json` | Version, tag, source commit, and packaging Node/npm versions                                                 |
| `SHA256SUMS`                             | SHA-256 digests of the three files above                                                                     |

Future releases using the integrated publisher additionally attach `release-notes.md`,
`release-notes.manifest.json`, `release-identity.json`, and `BUNDLE-SHA256SUMS`.
The first contains the same user-facing and engineering Markdown as the release
body; the second audits its range and producer. Existing v2.1.1 has only the four
historical runtime assets and is never rewritten.

The runtime archive is deliberately assembled from compiled output; `npm pack` is not the release artifact. It does not contain `node_modules`, development sources, tests, or fixtures. Runtime installation uses `npm ci --omit=dev --ignore-scripts`; see [runtime instructions](runtime.md). Checksums detect byte changes but do not independently prove publisher identity or build provenance.

## Permission separation

| Stage             | Elevated permissions and boundary                                                                      |
| ----------------- | ------------------------------------------------------------------------------------------------------ |
| Release Please    | `contents`, `issues`, and `pull-requests: write`; pinned automation, no checkout or project execution  |
| Dispatch          | `actions: write`; schedules validation/publication using validated metadata                            |
| Publish preflight | `contents: write` and `actions: read` to inspect drafts and native environment controls; metadata only |
| Native notes      | `contents: write` for non-saving generate-notes only; no checkout or downloaded artifact execution     |
| Validation        | `contents: read`; project code and dependencies run only in these read-only jobs                       |
| Provenance        | `id-token: write` and `attestations: write`; downloads tested assets, no project checkout/build        |
| Publication       | `contents: write` and `actions: read`; downloads and uploads tested assets, no rebuilding              |

Workflow actions are pinned by commit. Optional CLI update notices and OpenTelemetry are disabled (`GH_NO_UPDATE_NOTIFIER`, `GH_NO_EXTENSION_UPDATE_NOTIFIER`, `DO_NOT_TRACK`, `OTEL_SDK_DISABLED`). Required GitHub API, artifact and attestation service traffic and service-side audit logs remain; these controls do not claim otherwise. Ordinary PR title validation uses `pull_request_target` only to inspect metadata; it never executes PR code. The dispatched title check also verifies that it is checking the current release PR head.

## Repository settings

Terraform in [`governance/`](../governance/) manages the repository's settings; [Repository governance as code](governance.md) lists them with their verification. In short:

- Squash merging only, titled by the PR title with a blank body; merged branches are deleted.
- The default `GITHUB_TOKEN` is read-only; only GitHub-owned, verified-creator and the two listed third-party actions may run, each pinned to a full commit SHA.
- The `main` ruleset requires a pull request, passing `All checks` and `Conventional Commit PR title` checks on an up-to-date branch, resolved conversations, and linear history; it blocks force pushes and deletion and has no bypass.
- `v*` tags cannot be moved or deleted, and publication waits for the release approver in the `release` environment.
- Workflows from forks wait for approval before running, and never receive write tokens or secrets.

**Immutable releases** lock a release's assets and tag once it is published. Drafts remain editable, so publication attaches every asset to the draft first and then publishes it; published versions are never overwritten. GitHub's release attestation for immutable releases is a platform feature separate from build provenance.

**Build attestations** use the first-party [`actions/attest`](https://github.com/actions/attest) action, which GitHub recommends over the `attest-build-provenance` wrapper for new implementations. See [the attestation documentation](https://docs.github.com/en/actions/concepts/security/artifact-attestations).

## Merge-policy audit

The `main` ruleset enforces the merge policy. `main-policy-audit.yml` remains a **detective** check behind it: after every push to `main`, it reads metadata only and fails if any pushed commit:

- is not a single-parent squash commit, or has a subject that is not a Conventional Commit;
- did not arrive through a merged pull request based on `main`;
- came from a PR head without passing **All checks** and **Conventional Commit PR title** check runs; or
- was force-pushed.

It warns when the PR had no approval from someone other than its author. A failed audit means the policy was bypassed after the fact; investigate it and correct `main` through a new PR. Release publication separately revalidates the exact tagged commit, so an unchecked merge cannot publish without passing CI.

## Local verification

From a clean checkout with Node 24 and the documented npm 11.19.0. Archive packaging uses **GNU tar on Linux**, matching the GitHub runner:

```bash
npm ci --ignore-scripts
npm run check
npm run verify:version
npm run package:release
npm run test:artifact
```

`npm run check` produces `dist/`. Packaging reuses it; the artifact test extracts the archive into an isolated temporary directory, installs only locked runtime dependencies, and checks the compiled application. The full reusable CI adds the security, fuzzing, mutation, and performance gates described above. Release mutation validation always forces full execution and never trusts incremental result caches. Use `npm run mutation:full` for the same local guarantee.

## Release history

Versions 1.1.0 to 2.1.0 are recorded in the [changelog](../CHANGELOG.md), and their `chore(main): release X.Y.Z` commits are on `main`. GitHub Releases with downloadable, attested artifacts start with the first version published after 2.1.0.

## Verify a published release

Download every asset of one release into an empty directory, then check the digests, metadata, and runtime:

```bash
tag=vX.Y.Z
mkdir "release-$tag" && cd "release-$tag"
gh release download "$tag" --repo Lunary-Lab/mp3-frame-analyzer
sha256sum --check SHA256SUMS
gh release verify "$tag" --repo Lunary-Lab/mp3-frame-analyzer
gh attestation verify "mp3-frame-analyzer-${tag#v}.tar.gz" --repo Lunary-Lab/mp3-frame-analyzer \
  --signer-workflow Lunary-Lab/mp3-frame-analyzer/.github/workflows/publish-release.yml --source-ref "refs/tags/$tag"
jq . "mp3-frame-analyzer-${tag#v}.manifest.json"   # version, tag, sourceCommit
gh api "repos/Lunary-Lab/mp3-frame-analyzer/commits/$tag" --jq .sha   # must equal sourceCommit
```

Then follow [the runtime guide](runtime.md) to extract the archive, install production dependencies, upload an MP3, and stop the server with `SIGTERM`.

## Recover from a failed release

- **Release PR validation failed:** fix the cause in an ordinary PR. Release Please regenerates the release PR, and redispatches its checks, only when its title or notes change. Otherwise use the release PR's **Update branch** button; that human-initiated push runs the ordinary PR checks. Publication revalidates the tagged commit either way.
- **Publication failed after the draft and tag were created:** a retry runs the workflows and source from the tag, so changes merged to `main` cannot repair it. Retry the draft as shown below for transient failures, such as a runner or network error. If the tagged source or its workflows are defective, leave the draft unpublished, merge the fix, and let Release Please propose the next version. Never move or recreate a release tag.
- **A published release is defective:** published releases are immutable. Merge a correction and release a new version.

## Retry an unpublished draft

Set the existing draft tag and obtain its full 40-character commit SHA, then dispatch from that same tag:

```bash
release_tag=vX.Y.Z
release_sha="$(gh api "repos/Lunary-Lab/mp3-frame-analyzer/commits/$release_tag" --jq .sha)"
gh workflow run publish-release.yml \
  --repo Lunary-Lab/mp3-frame-analyzer \
  --ref "$release_tag" \
  -f "tag=$release_tag" \
  -f "sha=$release_sha"
```

Replace `vX.Y.Z` with the actual draft tag. Do not use **Re-run jobs**: attempts after the first are rejected. The newly dispatched run waits for a new approval in the `release` environment again. A `--ref main` invocation fails preflight, as does a changed tag, non-`main` source commit, mismatched SHA, or already-published release. Retrying may replace assets only while the release remains a draft. Publication is serialized and checks existing stable versions so retrying an older draft cannot move the `latest` designation backwards. For a published defect, merge a correction and release a new version.
