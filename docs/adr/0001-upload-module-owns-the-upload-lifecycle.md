# The upload module owns the upload lifecycle

The route used to inline two upload adapters, raw and multipart, that handled media type, size limit, empty uploads and the unread remainder of a rejected upload each in their own way. We moved both into `src/upload.ts` behind one interface: the route hands it a consumer, the frame counter, and never touches request bodies. The module also registers the raw content-type parser and the multipart plugin, so every per-upload limit lives in one place.

## Decisions

- **Original extraction and enforcement follow-up.** The original refactor preserved status codes and error bodies, with HTTP regressions for the exercised failures. This follow-up adds an aggregate multipart limit and deterministic handling of successful early consumers; those behavior changes and their bounds are recorded below.
- **The consumer is passed in.** The module knows nothing about MP3 parsing. It closes a started input iterator on consumer return/rejection, while normal EOF already finishes it. Raw early success closes after returning the consumer's result without draining. Multipart early success drains and validates the remainder before returning the result. A cleanup failure after success propagates; a secondary cleanup failure is logged while preserving the primary failure. Consumers must await their reads; arbitrary detached consumer work is outside this lifecycle contract.
- **Rejected remainders:** raw rejection closes after the response without draining. Multipart consumer rejection starts a background drain; field-name/media-type validation still awaits discarding the rejected part. A multipart-provider iteration failure closes after its response if raw EOF has not been consumed: the provider may have unpiped, so bounded draining is no longer guaranteed. Reuse requires complete body receipt within the aggregate cap and timeouts. A later malformed remainder or limit crossing does not replace a response already chosen.
- **Aggregate multipart budget (enforcement follow-up):** Busboy's file limit bounds delivered file bytes, not discarded HTTP body data. A separate `MAX_MULTIPART_BYTES` / `maxMultipartBytes` cap counts the transfer-decoded whole multipart body, including preamble, headers, ignored parts and epilogue. Its default is the file cap plus 64 KiB, saturated at `Number.MAX_SAFE_INTEGER`; this allowance is configurable project policy. Declared oversize rejects with sanitized `413 request-too-large`; streaming oversize stops consumption and closes after the selected response.
- **Backpressure and cleanup:** the guard pauses `request.raw` before adding its observer, then starts actual multipart iteration so the plugin installs/resumes its pipe. It never drives a second read loop. After overflow, a failure-only resume guard keeps body delivery paused, while retaining the pipe so a normal buffered EOF can still end Busboy. Removing that pipe early can strand multipart iteration even though the error response succeeds. The guard lasts until raw end/close, even after early rejection, and removes its own listeners. Node can still deliver the crossing chunk to the current listener snapshot, so acceptance is separately gated on the violation. Transport read-ahead is not a wire-byte guarantee. No whole-body buffering or arbitrary Content-Encoding decompression is introduced.
- **The parser's cleanup contract stays.** `countMp3Frames` closes its input when it fails, which is correct for any async iterable. The Busboy stall that closing causes is Node-stream knowledge, so the upload module reads files with `destroyOnReturn: false` instead of the parser changing.
- **Failures outside an upload** (an invalid query option, a body Fastify rejects before the route runs) are not the upload module's concern; the route and the error handler decide their connection disposition (refined by [ADR 0002](0002-one-pure-mapping-from-failure-to-error-response.md)).
- **One accepted media-type list** serves raw uploads and multipart file parts, as the HTTP specification already defines.

## Considered options

- **Hand the route a byte stream** and have it report parser failures back: rejected, because every caller would have to remember to report back, in order.
- **Call the frame counter inside the module:** rejected, because upload handling would then depend on MPEG parse errors to decide what to do with a remainder.

- **Only a Fastify preParsing transform:** rejected for this pinned plugin because it reads `request.raw` directly rather than the transformed payload.
- **Unbounded keep-alive draining:** rejected; file limits do not bound ignored body bytes. Closing every rejected multipart connection would also be safe, but would unnecessarily discard demonstrated reuse for bounded complete requests.
